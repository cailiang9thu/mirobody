# 阶段一 MVP 改造方案（0–3 个月）

> 对应 [rare-specs.md](rare-specs.md) §6「阶段一：MVP」。
> 目标：让 **DEE-SWAS 等首批病例**跑通一条完整的"表型 + 变异 → 候选基因"闭环，
> 并把闭环的每一步都落成**可复用的表和工具**，而不是一次性脚本。

---

## 0. MVP 边界

### 0.1 做什么（In scope）

| 编号 | 交付物 | 层 | 完成定义 |
| --- | --- | --- | --- |
| **D1a** | **病例文档解析** | 层1 前置 | 一份病例（叙述文本 + 图表）产出带主体归属、时间、否定标记的结构化断言 —— 见 §14 |
| **D1b** | HPO 表型编码与检索 | 层1 | D1a 的断言 → HPO term 落库，可按 term 检索患者 |
| D2 | VCF 摄取与变异表 | 层2 | 一个 WES VCF 上传后，变异逐条落 `th_variant` |
| D3 | ClinVar / gnomAD 注释 | 层2 | 每条候选变异带致病性分类与群体频率 |
| D4 | 原始信号存储 + 索引 | 层4 | MRI/EEG 原始文件可上传、可按元数据检索、不做解析 |
| D5 | 四个 MCP 工具 | 接口 | TRACES 通过统一 MCP 面拿到 D1–D4 的数据 |
| D6 | 三级同意模型 | 治理 | 每次数据使用都能回答"谁授权了什么用途" |
| D7 | 家系结构（条件性） | 层3 | 首批病例有 trio 才做；否则只建空表与 PED 导入 |
| **D8** | **疾病编码层（OMIM / Orphanet）** | 层1.5 | 病例中的疾病名映射到 OMIM/ORPHA 编码 —— 语料实测 191/192 例的疾病名是纯自由文本，见 §13.3 |
| **D9** | **语料与金标集** | 质量 | 30 份人工标注病例作为抽取质量基准，无此无法判断改 prompt 是变好还是变坏 |

### 0.2 不做什么（Explicitly out of scope）

**写在这里是为了防止 MVP 被这几件事拖垮**，它们每一件都是独立的季度级工程：

- ❌ **自建 ACMG 自动分级引擎** —— MVP 只承载 ClinVar 已有的 `clinical_significance`，外加一个供人工判读写入的字段。自动 ACMG 28 条规则实现属于阶段二。
- ❌ **WGS 级 VCF** —— MVP 只保证 panel / WES 规模（单样本变异数 < 500 万行，文件 < 500 MB）。WGS 需要分片摄取与列式存储，阶段二再谈。
- ❌ **影像/EEG 的结构化解析** —— 层4 MVP 只做"存储 + 去标识化元数据索引"，不做像素级或波形级特征抽取。
- ❌ **MatchMaker Exchange 对外广播** —— 需要先有稳定的候选变异质量和 IRB 授权，阶段二。
- ❌ **内部队列频率库** —— 样本量不够，阶段三。
- ❌ **图表的自动化视觉抽取**（表格位图 / 病程时间轴图）—— 语料实测证明关键数据确实藏在位图里（§13.4），但 MVP 只做**标注并转人工**，不做自动 OCR 结构化。
- ❌ **重跑 `mirobody/res/` 的 FHIR bundle build** —— 见 §3.1，MVP 用旁路方案绕开它。

### 0.3 四条硬约束

改造必须在现有工程纪律内完成，否则会被 CI 直接挡下：

1. **不改主干**：`engine.py` / `units/` / `lexical.py` / `kernel/` 的公开行为不变。
2. **遵守 import-linter 五条契约**（`pyproject.toml:399`）：库层只能依赖 numpy；engine 不得 import agent 层；`collect` 和 `translate` 各只有一个前门。新代码必须先想清楚放在契约的哪一侧。
3. **schema 只追加**：新 DDL 以下一个空闲前缀新建文件（`a5_` 之后是 `a6_`…），每个文件必须可重放（`IF NOT EXISTS` / `ON CONFLICT DO NOTHING`），不得回填进 baseline。
4. **wheel 不膨胀**：`scripts/check_wheel_data.py` 是硬闸。罕见病的大体积词表/注释库走 `mirobody/res/EXTERNAL.tsv` 外部下载，不进 git、不进 wheel。

## 2. 总体落点：一个插件包 + 四个 schema 文件

```
mirobody-rare/                         ← 新建独立发行包（不进主包 wheel）
├── pyproject.toml                     [project.entry-points."mirobody.tools"]
│                                        rare = "mirobody_rare.tools"
├── mirobody_rare/
│   ├── hpo/          层1：HpoAdapter（实现 DomainAdapter ABC）+ bundle 读取
│   ├── variant/      层2：VCF 解析、ClinVar/gnomAD 注释、过滤规则
│   ├── signal/       层4：DICOM/EDF 元数据抽取 + 去标识化
│   ├── pedigree/     层3：PED 导入、共分离计算（阶段一只建骨架）
│   ├── consent/      治理：三级同意校验
│   └── tools.py      四个 MCP 工具，*Service 命名以被自动注册
│
mirobody/schema/                       ← 主包，只追加 DDL
├── a6_phenotype.sql                   层1
├── a7_variant.sql                     层2
├── a8_signal_index.sql                层4
└── a9_pedigree_consent.sql            层3 + 同意
```

**为什么业务代码走插件包而不是进主包**：主包 `pip install mirobody` 是 2 包 67 MB 的库，罕见病依赖（`pysam` / `pydicom` / `pyedflib`）会把它撑成另一个东西，而 `mirobody.tools` entry point 本来就是为这个设计的 —— 装上即注册，同一个 registry、同一个 `/mcp` 面。

**一个已知缺口，必须在 W1 补掉**：插件包**没有 schema 注入扩展点**，`Server.start()` 只重放 `mirobody/schema/*.sql`。MVP 的取舍是 **DDL 放主包**（追加式、`IF NOT EXISTS`、对现有部署零影响），插件包只带代码。若阶段二要让插件自带 DDL，再给 `Server.start()` 加一个"收集 entry point 提供的 schema 目录"的小改。

> ⚠️ 部署提醒：手工建表必须 `export PGOPTIONS="-c search_path=$PG_SCHEMA"`。schema README 已记录 `a5_medications.sql` 因漏掉这一步落进 `public` 导致工具报内部错误的事故，新四个文件同样会踩。

## 3. D1 — 层1：HPO 表型层

### 3.1 关键决策：独立 adapter，**不**动 `SYSTEMS`

把 HPO 追加成 `SYSTEMS[6]` 是最"正统"的做法，MVP **不这么做**，理由是成本不对称：

- `SYSTEMS` 的索引被打包进持久化的 `fhir_id`（`sys<<60|code`）和 `fhir_code_index.csv.gz`，追加意味着**必须重跑 bundle build**；
- 而 bundle build 需要 UMLS / SNOMED CT / LOINC / RxNorm 四份许可和一个约 200 MB 的语义矩阵（`docs/vocabulary-build.md`），还要重新发布 22 MB 的 `fhir_concept_graph.bin`（走 `EXTERNAL.tsv` 的 `data-YYYY-MM-DD` release）；
- 这是一次有准备的发布任务，不该挡在首批病例前面。

**MVP 方案**：`HpoAdapter(DomainAdapter)` —— 自有 ID 空间、自有 bundle、自有图谱二进制，与 FHIR 侧完全隔离。跨本体映射用 crosswalk 文件在**结果层**联合，不需要共享 ID 空间：

```
mirobody/res/EXTERNAL.tsv   新增两行（need=runtime）
  hpo_bundle.tar.gz         HPO term + 同义词 + is_a 层级 + 修饰符轴
  hpo_snomed_crosswalk.tsv  HPO 官方 HPO↔SNOMED CT 映射表
```

保留升级路径：阶段二若确认需要图谱级联通（例如让"癫痫发作"从 SNOMED 侧也能召回 HP:0001250），再把 HPO 追加为 `SYSTEMS[6]` 并一次性重建 —— 4 bit 系统位还有 10 个空位，这条路没被堵死。

### 3.2 DDL：`a6_phenotype.sql`

```sql
CREATE TABLE IF NOT EXISTS th_phenotype (
    id              INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id         VARCHAR(200) NOT NULL,
    hpo_id          VARCHAR(16)  NOT NULL,        -- 'HP:0001250'
    hpo_label       TEXT         NOT NULL,        -- 落库时的标签快照，HPO 改名不影响回溯
    -- HPO 原生修饰符，全部可空：没观察到 ≠ 没有
    onset_hpo_id    VARCHAR(16),                  -- HP:0003593 Infantile onset ...
    severity_hpo_id VARCHAR(16),                  -- HP:0012825 Mild / Moderate / Severe
    frequency_hpo_id VARCHAR(16),                 -- HP:0040280 Obligate ... HP:0040285 Excluded
    -- 否定断言。HPO 的 "excluded" 是一等信息，不能用"没这行"表示
    negated         BOOLEAN NOT NULL DEFAULT false,
    -- 来源与可审计性
    source          VARCHAR(32) NOT NULL,         -- clinician | nlp | import
    source_text     TEXT,                         -- NLP 映射时的原始自由文本
    confidence      REAL,                         -- NLP 置信度；clinician 来源为 NULL
    asserted_at     TIMESTAMPTZ,                  -- 症状被记录的时间（≠ 入库时间）
    file_id         BIGINT,                       -- 溯源到 th_files
    deleted         BOOLEAN NOT NULL DEFAULT false,
    create_time     TIMESTAMPTZ NOT NULL DEFAULT now(),
    update_time     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_th_phenotype_user ON th_phenotype (user_id) WHERE NOT deleted;
CREATE INDEX IF NOT EXISTS idx_th_phenotype_hpo  ON th_phenotype (hpo_id)  WHERE NOT deleted;
```

三个设计点值得单独说：

- **`hpo_label` 存快照**：HPO 每季度发布，term 会改名甚至废弃（obsolete + `replaced_by`）。存标签快照才能解释"当时医生说的是什么"。
- **`negated` 是一等公民**：罕见病鉴别诊断里"明确排除了肝脾肿大"和"没问过肝脾肿大"是完全不同的证据强度。用"表里没这行"表达否定会直接误导推理引擎。
- **`source` 区分 clinician / nlp**：NLP 映射的 term 和医生手动确认的 term 权重不同，TRACES 必须能分辨。

### 3.3 映射链路

```
自由文本症状 ──► 候选 HPO term（lexical + 向量召回，HpoAdapter.resolve_many）
                    │
                    ├─ 高置信唯一命中 ──► 自动落库，source='nlp'
                    └─ 歧义 / 低分   ──► 进人工确认队列，落库时 source='clinician'
```

**不自动落库低置信结果**，这是 §0.3 "拒绝猜测"在层1 的具体形态。批量映射一律走 `resolve_many`（README 记录比循环 `resolve()` 快 20–30×）。

### 3.4 中文支持

首批病例是中文病历。HPO 官方有中文翻译（`hpo-translations`），但覆盖率与质量不均。做法与主包一致：把中文同义词进 `hpo_bundle` 的 alias 轴，复用 `mirobody/lexical.py` 的 CJK 分词器和 `zh_fold.py` 折叠 —— 这两个模块在库层（numpy-only 契约内），插件包 import 它们是合法的。

## 4. D2 + D3 — 层2：变异级基因组

### 4.1 关键决策：新建表，不动 `th_series_data_genetic`

`th_series_data_genetic` 保留原样服务消费级芯片场景。变异表是**另一类数据**（不同来源、不同置信度、不同法律含义），混表会让"这个 A/G 是芯片探针还是测序 call"这个问题无法回答。

### 4.2 DDL：`a7_variant.sql`

```sql
-- 一次测序 = 一个 sample。VCF 的样本列、测序类型、参考基因组版本挂这里。
CREATE TABLE IF NOT EXISTS th_sequencing_sample (
    id            INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id       VARCHAR(200) NOT NULL,
    file_id       BIGINT,                          -- th_files，原始 VCF
    assay         VARCHAR(16)  NOT NULL,           -- WES | WGS | PANEL | RNASEQ
    reference     VARCHAR(16)  NOT NULL,           -- GRCh37 | GRCh38 —— 不可省略
    sample_label  VARCHAR(128),                    -- VCF 里的样本列名
    caller        VARCHAR(64),                     -- GATK / DeepVariant / ...
    called_at     DATE,
    status        VARCHAR(16) NOT NULL DEFAULT 'pending',  -- pending|parsing|annotating|ready|failed
    variant_count INTEGER,
    create_time   TIMESTAMPTZ NOT NULL DEFAULT now(),
    update_time   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS th_variant (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sample_id   INTEGER NOT NULL REFERENCES th_sequencing_sample(id),
    user_id     VARCHAR(200) NOT NULL,             -- 冗余，避免每次查询都 join
    -- 变异身份：VCF 五元组，GA4GH 规范化（左对齐 + 去冗余碱基）后存储
    chrom       VARCHAR(8)  NOT NULL,
    pos         INTEGER     NOT NULL,
    ref         TEXT        NOT NULL,
    alt         TEXT        NOT NULL,
    -- 基因型与质量
    genotype    VARCHAR(8),                        -- 0/1, 1/1, 0|1 ...
    zygosity    VARCHAR(16),                       -- het | hom | hemi
    depth       INTEGER,                           -- DP
    gq          INTEGER,                           -- GQ
    filter      VARCHAR(64),                       -- VCF FILTER 列，PASS 与否
    -- 基因注释（来自 VEP / SnpEff，MVP 取 most severe consequence）
    gene_symbol VARCHAR(64),
    hgvs_c      TEXT,
    hgvs_p      TEXT,
    consequence VARCHAR(64),                       -- missense_variant / stop_gained ...
    -- 遗传模式判定，家系齐备时才能填；空值 = 未知，不是 false
    is_de_novo  BOOLEAN,
    inheritance VARCHAR(16),                       -- de_novo | maternal | paternal | unknown
    create_time TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_th_variant_call UNIQUE (sample_id, chrom, pos, ref, alt)
);
CREATE INDEX IF NOT EXISTS idx_th_variant_user_gene ON th_variant (user_id, gene_symbol);
CREATE INDEX IF NOT EXISTS idx_th_variant_locus     ON th_variant (chrom, pos);

-- 注释与变异分离：ClinVar/gnomAD 按月更新，注释会变，call 不会变。
CREATE TABLE IF NOT EXISTS th_variant_annotation (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    variant_id   BIGINT NOT NULL REFERENCES th_variant(id),
    source       VARCHAR(32) NOT NULL,             -- clinvar | gnomad | manual
    source_version VARCHAR(32) NOT NULL,           -- 'clinvar_20260901' / 'gnomad_v4.1'
    -- ClinVar
    clinical_significance VARCHAR(64),             -- Pathogenic / VUS / Benign ...
    review_status         VARCHAR(64),             -- ClinVar 星级，决定这条注释值多少
    condition_names       TEXT[],
    -- gnomAD
    af_global    DOUBLE PRECISION,
    af_popmax    DOUBLE PRECISION,
    popmax_pop   VARCHAR(16),
    allele_count INTEGER,
    -- 人工判读（MVP 不自动生成，只承载）
    acmg_class   VARCHAR(8),                       -- P / LP / VUS / LB / B
    acmg_codes   TEXT[],                           -- PVS1, PS2, PM2 ...
    asserted_by  VARCHAR(200),
    note         TEXT,
    create_time  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_th_variant_annotation UNIQUE (variant_id, source, source_version)
);
```

设计要点：

- **`reference` 不可省略**。GRCh37 和 GRCh38 的同一坐标是不同位点，混存会产生静默错误（最危险的一类）。
- **注释独立成表、带 `source_version`**。ClinVar 每月改判，把 `clinical_significance` 写死在 `th_variant` 上就永远解释不了"三个月前为什么判成致病"。
- **`is_de_novo` 三态**。`NULL`（没有父母数据，未知）≠ `false`（查过了，是遗传的）。这正是 `rare-specs.md` 说的"新发突变富集度统计的基础，必须一开始就规范建表"。
- **`review_status`（ClinVar 星级）必须带**。零星的 ClinVar "Pathogenic" 和三星专家共识的可信度差一个量级，不带星级等于把噪声当证据。

### 4.3 摄取链路：`VcfHandler`

`collect/files/handlers/factory.py:38 get_handler()` 目前第一步就是 `GeneticHandler.is_genetic_file()`（WeGene 魔术串）。在它**之前**插入 VCF 判定：

```python
# factory.py，在 GeneticHandler 分支之前
if await VcfHandler.is_vcf_file(file):        # 头部含 '##fileformat=VCFv4'
    return VcfHandler(...)
```

**关键差异：VCF 必须旁路现有文本抽取链路。** 现有 handler 会把文件内容抽成 `original_text` 再交给 `indicator_extractor`/`abstract_extractor` 走 LLM。一个 WES VCF 有数十万行，走这条路既昂贵又无意义。`VcfHandler` 的职责收窄为三步：

```
1. 原样存对象存储（复用 th_files.file_key + content_hash 去重），
   original_text 留空、text_length = 0
2. 建 th_sequencing_sample 行，status='pending'
3. spawn 异步解析任务（复用 mirobody/utils/tasks.py:spawn，
   GeneticHandler 已是这个模式），HTTP 立即返回
```

异步解析任务按 **CLAUDE.md 的分批并发不重来**原则实现：
- 按染色体分片，`asyncio` 并发 ≤8；
- 每片完成即写 `th_variant` 并推进 `th_sequencing_sample` 的进度；
- 重跑先扫已写入的 `(sample_id, chrom)` 集合，只跑缺失分片，不整批重来（`uq_th_variant_call` 唯一约束兜底幂等）。

### 4.4 注释链路：先本地收窄，再打 API

`rare-specs.md` 说"直接调 gnomAD API"。**顺序很重要**，一个 WES 样本有 3–5 万个变异，逐个打 gnomAD GraphQL API 会触发限流且要跑几小时。正确顺序是**先用零成本的本地过滤把候选收到几百个，再打 API**：

```
3~5 万 raw calls
  │
  ├─① 质控：FILTER = PASS、DP ≥ 10、GQ ≥ 20                     ── 本地，免费
  ├─② 后果过滤：只留编码区 + 剪接位点（missense / LoF / splice） ── 本地，免费
  ├─③ ClinVar 本地表命中（全量 ClinVar VCF 约 200 MB，
  │     走 EXTERNAL.tsv 月更）                                   ── 本地，免费
  ├─④ HPO 驱动的基因优先级：用 D1 的表型集合，
  │     经 HPO-基因关联（genes_to_phenotype.txt）给基因打分      ── 本地，免费
  │
  └──► 候选 200–500 条 ──► gnomAD API 批量查频率 ──► 过滤 AF_popmax > 0.01
                                                    ──► 写 th_variant_annotation
```

④ 是层1 和层2 在 MVP 里真正**咬合**的地方 —— 也是"两层是诊断闭环最小必要集"这句话的技术含义。缺了层1，层2 的候选集收不下来。

## 5. D4 — 层4：原始信号（存储 + 索引）

### 5.1 范围

只做三件事：**原样存、去标识化、建元数据索引**。不解析像素、不解析波形。

### 5.2 DDL：`a8_signal_index.sql`

```sql
CREATE TABLE IF NOT EXISTS th_signal_object (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id      VARCHAR(200) NOT NULL,
    file_id      BIGINT NOT NULL,                  -- th_files，原始文件与对象存储 key
    modality     VARCHAR(16) NOT NULL,             -- MRI | CT | EEG | WSI | OTHER
    format       VARCHAR(16) NOT NULL,             -- DICOM | EDF | DICOM-WSI
    -- 去标识化后的元数据；原始 header 的 PHI 字段一律不落库
    body_part    VARCHAR(64),
    study_date   DATE,
    series_desc  TEXT,
    instance_count INTEGER,
    duration_sec   INTEGER,                        -- EEG 时长
    channel_count  INTEGER,                        -- EEG 导联数
    -- 报告结论摘要（若随附报告文档）
    report_summary TEXT,
    report_file_id BIGINT,
    -- 数据主权标记，见 §7
    residency    VARCHAR(8) NOT NULL DEFAULT 'CN', -- CN | US | EU
    exportable   BOOLEAN NOT NULL DEFAULT false,
    deid_status  VARCHAR(16) NOT NULL DEFAULT 'pending',  -- pending|done|failed
    create_time  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_th_signal_user_modality ON th_signal_object (user_id, modality);
```

### 5.3 去标识化是 MVP 必做项，不是延后项

DICOM header 默认携带患者姓名、出生日期、病历号、设备序列号、有时还有操作者姓名。**上传即入库 = 未经处理的 PHI 直接落表。** 因此：

- 入库前跑 DICOM de-identification（DICOM PS3.15 Annex E Basic Application Level Confidentiality Profile），`deid_status` 未到 `done` 的对象不对上层工具可见；
- 原始文件保留在对象存储（诊断可能需要原图），但访问受 §7 的同意检查；
- EDF header 同理（`patient identification` 字段）。

这一条不能因为"MVP 只做存储"就跳过 —— 存储正是 PHI 泄露发生的地方。

## 6. D7 — 层3：家系（条件性）

### 6.1 为什么不直接复用 `care_circles`

`care_circles` 看起来很像家系，但两者语义正交：

| | care_circle | pedigree |
| --- | --- | --- |
| 表达的是 | **授权**关系（谁能看谁的记录） | **生物学**关系（谁是谁的亲生父母） |
| 关系方向 | `health_access` 由数据主人自己设，别人不能调高 | 父子关系是客观事实，不由任何一方"设置" |
| MVP 需要的语义 | —— | "父母数据参与共分离计算，但不返回其个体诊断结论" |

最后一行是关键：现有模型只有 0/1/2 三档读写权限，**表达不了"可计算、不可返回"**。硬套 `care_circles` 会把一个合规要求偷偷降级成一个权限位。

### 6.2 DDL：`a9_pedigree_consent.sql`（家系部分）

```sql
CREATE TABLE IF NOT EXISTS th_pedigree (
    id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    family_id   VARCHAR(64) UNIQUE NOT NULL,       -- PED 第 1 列
    label       VARCHAR(256),
    create_time TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS th_pedigree_member (
    id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    pedigree_id INTEGER NOT NULL REFERENCES th_pedigree(id),
    user_id     VARCHAR(200),                      -- 可空：未建档的家庭成员也要能进谱系
    individual_id VARCHAR(64) NOT NULL,            -- PED 第 2 列
    paternal_id VARCHAR(64),                       -- PED 第 3 列，'0' → NULL
    maternal_id VARCHAR(64),                       -- PED 第 4 列
    sex         SMALLINT,                          -- PED 第 5 列：1 男 2 女 0/NULL 未知
    affected    SMALLINT,                          -- PED 第 6 列：1 未患病 2 患病 0/NULL 未知
    is_proband  BOOLEAN NOT NULL DEFAULT false,
    -- 这个成员的数据可以被怎么用。MVP 的核心新语义。
    analysis_only BOOLEAN NOT NULL DEFAULT false,  -- true = 参与计算，不返回个体结论
    create_time TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_pedigree_individual UNIQUE (pedigree_id, individual_id)
);
```

### 6.3 阶段一做到哪

- **必做**：建表 + PED 文件导入 + `th_variant.is_de_novo` / `inheritance` 的 trio 填充逻辑（有 trio 数据时）。
- **延后**：完整共分离统计（多代、多分支、外显不全建模）留阶段二。

`analysis_only` 即使在没有 trio 数据的情况下也要在 MVP 建好 —— 它是个数据模型语义，事后加需要回溯所有已有记录的合法性。

## 7. D6 — 三级同意模型

### 7.1 DDL：`a9_pedigree_consent.sql`（同意部分）

```sql
CREATE TABLE IF NOT EXISTS th_consent (
    id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     VARCHAR(200) NOT NULL,
    -- 三级授权，分别勾选，不打包
    scope       VARCHAR(24) NOT NULL,   -- individual_return | research_use | commercial_use
    granted     BOOLEAN NOT NULL,
    -- 谁签的。未成年人由监护人签，必须记录签署主体。
    signed_by_user_id VARCHAR(200) NOT NULL,
    relationship      VARCHAR(24),      -- self | guardian
    -- 适用的数据层，NULL = 全部
    layer       VARCHAR(16),            -- phenotype | variant | signal | pedigree
    -- 数据主权
    residency   VARCHAR(8),             -- CN | US | EU
    cross_border_allowed BOOLEAN NOT NULL DEFAULT false,
    effective_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at   TIMESTAMPTZ,
    document_file_id BIGINT,            -- 签署的同意书原件，th_files
    CONSTRAINT uq_th_consent_live UNIQUE (user_id, scope, layer, effective_at)
);
```

### 7.2 执行点

同意不能只是一张表，必须有唯一的**执行喉咙**。现有架构已有先例：`user/care_circle.py::accepted_membership` 是所有授权判断的唯一入口。照抄这个形态：

```
mirobody_rare/consent/gate.py::permit(caller_id, subject_id, layer, purpose) -> bool
```

四个 MCP 工具在 `_run` 之前**全部**过这个函数，没有例外路径。`analysis_only` 成员的个体结论在这里被拦下。

## 8. D5 — TRACES 接口：四个 MCP 工具

### 8.1 工具面

按 `agent/tools/README.md` 的发现规则，类名以 `Service` 结尾即自动注册、自动由类型注解生成 schema：

| 工具 | 回答的问题 | 参照实现 |
| --- | --- | --- |
| `query_phenotype` | 这个患者/家系有哪些 HPO term？哪些被明确排除？ | `health_indicators_service.py` |
| `query_variant` | 这个患者在这些基因/区间上有哪些变异？致病性与频率如何？ | `genetic_service.py` |
| `query_signal_index` | 这个患者做过哪些影像/EEG？能取到原始文件吗？ | 新 |
| `query_pedigree` | 家系结构是什么？哪个变异是 de novo？ | 新 |

四个都走 `RecordTool` 的三步壳（authorize → run → render）+ `tools.Envelope`，与现有工具形态一致。TRACES 通过 `POST /personal/mcp` 拿到的同一个 MCP URL 访问，**不需要为罕见病另建一套接口**。

### 8.2 每个工具必须带的 caveat（继承"拒绝猜测"）

`genetic_service.py` 给每个答案强制附 `_ABSENCE_NOTE`（"缺失 ≠ 未携带"）和 `_UNPHASED_NOTE`（"邻近 ≠ 连锁"）。这个做法在罕见病场景下更重要 —— 推理引擎最容易在这四个地方得出相反结论：

| 工具 | 必带声明 |
| --- | --- |
| `query_phenotype` | 表里没有某 term = **未评估**，不等于该表型不存在；`negated=true` 才是"已排除" |
| `query_variant` | WES 不覆盖内含子深部、UTR、结构变异和重复扩增；阴性结果不排除遗传病因 |
| `query_variant` | `af_global` 为空 = **未查询**，不等于该变异在人群中不存在 |
| `query_pedigree` | `is_de_novo = NULL` = 无父母数据，不等于遗传自父母 |

这不是文档措辞，是**工具返回值的一部分**，随每次调用发出。

| 风险 | 影响 | 缓解 |
| --- | --- | --- |

## 12. 一句话总结（MVP 核心）

**MVP 就是把层1 和层2 咬合起来跑通一次**：HPO 表型把基因优先级算出来，变异表靠这个优先级把三万个 call 收窄到几百个，再打 gnomAD 定性 —— 层4 只管把原始信号安全地存下来别泄露 PHI，层3 有 trio 就做没有就建空表。所有新代码走 `mirobody.tools` 插件包不碰主包，所有新表走 `a6`–`a9` 追加式 DDL 不动 baseline，所有工具继承 `genetic_service.py` 那套"缺失不是阴性"的强制声明。

## 13. 病例语料实测：`rareDieaseCollect`

扫描对象：`/home/gendata/caill/mirobody_rare/data/rareDieaseCollect`（700 MB / 3357 文件）。
本节全部数字来自实际扫描，不是估计。

### 13.1 语料是什么 —— 以及**不是**什么

先纠正一个可能的误解：**这批数据是公开发表的病例报告，不是患者的原始就诊资料。**

| 语料 | 在盘例数 | 正文形态 | 中位篇幅 | 图片 |
| --- | --- | --- | --- | --- |
| `罕见病病例_专业`（hjbxjz 汇总的医院专栏/文献翻译） | 192 | `content.json` 已按章节切好：病史摘要 184、讨论 131、检验检查 77、诊疗经过 69、诊断思路 57 | 3106 字 | 1326 张 |
| `罕见病病例_患者咨询`（患者自述 + AI 咨询） | 30 | 病史描述 30、相关检查 30、求助信息 27 | 609 字 | 占位图，无实质内容 |
| `罕见病研究期刊病例`（《罕见病研究》开放获取） | 84 | `body_markdown` + `article.pdf`，**born-digital，无需 OCR**（实测 7 页 13 624 字文本层） | 9000+ 字 | 229 张 |

**这对 MVP 意味着两件事：**

1. **它不能当生产输入的代用品。** 真实病例是扫描件、手机翻拍、手写病程记录；这批语料是已经排版清洗过的发表文本。`rare-mvp-plan.md` §A 里"OCR 从旁路变成主路径"的判断，**这批数据验证不了**，需要另找真实就诊资料来验证。
2. **它是极好的评测与词表语料。** 公开、无 PHI、覆盖 300+ 种罕见病、带完整诊断结论 —— 这正是 D9 金标集和 D1b 中文同义词挖掘需要的东西，而且**没有伦理门槛**，可以立刻开工，不必等 IRB。

### 13.2 三个数据完整性问题（须先处理）

| 问题 | 实测 | 处理 |
| --- | --- | --- |
| **PMC 727 例缺失** | `catalog_全部.csv` 有 1033 行，磁盘只有 306 例；`PMC罕见病病例/` 目录**不存在** | 重跑 `scrape_pmc.py`（脚本支持断点续爬），或确认是有意删除。英文语料对校验 HPO 原生标签很有价值，不该缺 |
| **图片重复 24%** | 1585 个文件仅 1199 个唯一 hash；单张图最多重复 34 次（团队介绍/专家头像/二维码） | 入库前按 md5 去重。这直接决定视觉处理成本 —— 24% 是白烧的钱 |
| **HTML 标签残留** | 标题里出现 `<i>MYH9</i>`、`<i>SAMD9</i>/<i>SAMD9L</i>` | 清洗管线补一步去标签；基因名被标签切开会导致识别失败 |

### 13.3 语料实测印证的解析问题（带数字）

| 问题 | 实测比例 | 后果 |
| --- | --- | --- |
| **教学选择题污染** | 专业病例 **70/192（36%）** 正文中嵌有 `A、… B、… 以下…？` 形式的考题 | 抽取器会把**选项当症状抽出来**。例如某 MS 病例的"病史摘要"末尾直接跟着"以下符合多发性硬化常见的症状是？A、呼吸困难 B、视力下降…"——"呼吸困难"是干扰项，不是该患者的表型。**这是当前最高优先级的语料过滤项** |
| **否定/正常表述** | **94%**（181/192）含 `未见 / 无明显 / 阴性 / 正常 / 否认 / 未发现` | 且大量是**打包否定**：一句"血沉、糖化血红蛋白、感染性疾病筛查、甲功三项、AFP、CEA、肝肾功、心肌酶均正常"一次否定 9 项。抽取器必须能展开列表并逐项标 `negated` |
| **家族成员混入先证者叙述** | **57%**（111/192）含家族成员表述 | 实例："患者有3姐1妹，其中1姐（早产儿）和1妹均有出生后出现癫痫、构音障碍…现均已过世"——这段**既是污染源也是金矿**：抽错主体会把姐妹的表型记到先证者头上，抽对了则直接给出常染色体隐性的共分离证据 |
| **疾病名无编码** | **191/192 不含 OMIM/Orphanet 标识** | 疾病名 100% 是自由文本（"2-羟基戊二酸尿症"、"Danon 病"、"肝豆状核变性"、"骨膜增生厚皮症"）。**这坐实了 D8 是真缺口**，不是锦上添花 |
| **HGVS 记法稀缺** | 仅 **32/192** 含 `c.` / `p.` / `NM_` 记法 | 大部分病例只说"基因检测发现 LAMP2 基因突变"，没有位点。层2 的变异表从病例文本里**填不满**，必须靠原始 VCF/报告 |
| **缩写歧义** | 高频符号里 `TSC`/`SMA`/`MPS`/`HLH`/`NF1` 既像基因符号又是疾病缩写 | 纯正则抽基因名会产生大量假阳性。基因识别必须走 HGNC 词表校验，不能靠大写字母模式 |

**真实语料噪声样本**（取自患者咨询 001，一例 2-羟基戊二酸尿症）：

- 错别字：`已酰肉碱`（应为**己**酰肉碱 C6）、`葵酰肉碱`（应为**癸**酰肉碱 C10）、`小脑蚯萎缩`（应为**蚓**部）
- 非标准单位：`0.39uM`（应为 µmol/L，UCUM 归一化对象）
- 相对时间：`抽搐26年`、`近2年出现言语不清`、`1岁时出现癫痫`
- 既往误诊：`曾就诊北京、上海等多家医院，诊断"癫痫"` —— 26 年的错误诊断，是**前医生的断言**不是事实
- 既往假设：`故考虑遗传代谢病可能` —— 必须标记 asserted-by-whom，否则 TRACES 会形成回音室
- 治疗反应作为表型证据：`出院后1月随访，患者未再发癫痫…智能改善，可认人`

### 13.4 关键发现：**核心数据藏在位图里**

专业语料 1088 张 PNG 中，868 张是横宽图（影像/图表）、72 张竖长、148 近方形。抽样查看后确认，**图不是插图，是数据本身**：

- `018_…围产期致死性戈谢病/images/16691706013270152.png` —— 一张 **28 行的基因型-表型对照表**，列为 `GBA Variant 1 / Variant 2 / Hydrops / Ichthyosis / Hepatosplenomegaly / Thrombocytopenia / Neurology / ERT / Death`，单元格是 `+ / − / NA` 三态。变异写作 `p.L483R`、`c.1447-1466del20insTG`、`RecNciI`。**这张表的全部内容只存在于像素里，正文一字未提。**
  - 附带风险：`RecNciI` 在图中易被 OCR 读成 `RecNci1` / `RecNcil` —— **变异名里的 I/l/1 混淆会产生静默错误**。
  - 好消息：`+ / − / NA` 三态与 `th_phenotype` 的 `negated` + 缺行语义正好对应，schema 接得住。
- `007_…FUS突变MS与ALS并发/images/16613944968973472.png` —— 一张 **28 年病程时间轴**：1993 起病 → 四次复发（各带 EDSS 评分）→ 用药区间（β干扰素 1996-2004、硫唑嘌呤 2004-2014、芬戈莫德因白细胞减少停药）→ 2021 死亡。**整个时间轴只存在于图里。**

**结论**：`rare-mvp-plan.md` §0.2 原先把层4 定为"只存不解析"是对的，但**遗漏了一类**——病例文档里的**数据型图表**既不是原始信号（不归层4），也进不了文本抽取链路。MVP 的处理是：**检出并标记，转人工录入**，不做自动化视觉结构化（见 §14.3）。

## 14. D1a：病例文档解析管线

### 14.1 为什么不能复用 `indicator_extractor`

现有 `prompts/file_indicator_extract.py` 的 STEP 1 就把目标框死为 **medical examination report**，产出是"项目-数值-单位-参考区间"四元组。把一份出院小结喂进去，它会抽走里面嵌的几个化验值，**把整段叙述性表型丢掉** —— 这不是 bug，是它的设计目标。

因此 D1a 是**一条独立管线，独立 prompt，独立输出 schema**，与 `indicator_extractor` 并列而非替换。数值型指标仍然交给现有链路（`th_series_data`），叙述型表型走新链路（`th_phenotype`）。

### 14.2 输出 schema：断言（assertion）而不是 term

D1a 的产出不是 HPO ID —— 编码是 D1b 的事。D1a 产出的是**带上下文的临床断言**：

```jsonc
{
  "assertions": [{
    "text": "剪刀样步态",           // 原文片段，逐字，不改写
    "subject": "proband",          // proband | father | mother | sibling | other_relative | unknown
    "subject_hint": "1姐",          // 原文里对主体的称呼，供人工核对
    "polarity": "present",         // present | absent | uncertain   ← 对应 94% 的否定表述
    "kind": "phenotype",           // phenotype | lab_value | imaging | treatment | diagnosis_hypothesis
    "onset_text": "1岁时",          // 原文时间表述，不解析成绝对时间
    "asserted_by": "clinician",    // clinician | patient | prior_clinician  ← 26年误诊要能区分
    "section": "病史描述",
    "char_span": [128, 133],       // 溯源到字符级
    "page": null                   // PDF 来源时填
  }],
  "unparsed_figures": [{           // §13.4 的位图表格/时间轴
    "image": "images/1669....png",
    "reason": "data_table_in_raster",
    "needs_human": true
  }]
}
```

四个字段是罕见病特有、常规健康数据完全不需要的：`subject`、`polarity`、`asserted_by`、`onset_text`。**它们必须在抽取时一次产出**——事后从 HPO ID 反推主体是不可能的。

### 14.3 管线七步

```
① 语料过滤   去教学选择题（36%）、去 HTML 标签、去团队/专家介绍章节
② 章节路由   专业病例已有 sections 可直接用；期刊走 body_markdown；
              患者咨询按 病史描述/相关检查 分流
③ 图片分流   md5 去重（省 24%）→ 分类：数据表格 / 病程图 / 影像图 / 装饰图
              前两类进 unparsed_figures 转人工，后两类只存不读
④ 断言抽取   §14.2 的 schema，LLM 抽取，逐条带 char_span
⑤ 主体消解   subject 字段的二次校验：一段话里主语切换是最常见的错误源
⑥ 数值分流   kind=lab_value 的断言转交现有 indicator_extractor 链路 + UCUM 归一
⑦ 人工确认   polarity=uncertain、subject=unknown、needs_human 的全部入队
```

第 ① 步不是清洗小事：**36% 的污染率意味着不做这一步，超过三分之一的病例会被注入干扰项表型。**

### 14.4 D9 金标集设计

30 份人工标注，按语料比例分层抽样（专业 19 / 患者咨询 3 / 期刊 8），标注 §14.2 的全部字段。评测指标分开算，因为它们的失败代价不同：

| 指标 | 目标 | 为什么单列 |
| --- | --- | --- |
| 断言召回率 | ≥ 0.85 | 漏掉表型 = 诊断线索丢失 |
| `polarity` 准确率 | **≥ 0.95** | 把"未见异常"抽成"有异常"是**方向性错误**，代价远高于漏抽 |
| `subject` 准确率 | **≥ 0.95** | 抽错主体直接污染家系分析 |
| `asserted_by` 准确率 | ≥ 0.90 | 防止前医生的假设被当成事实 |
| 图表检出率 | ≥ 0.90 | 漏检 = 关键数据静默丢失（§13.4） |

金标集是**换 prompt / 换模型的唯一裁判**。没有它，D1a 的任何"优化"都无法证明是改进。

## 16. 编码参考库:从进程内存迁到 Postgres(2026-09-21 补充)

> 触发:层1/层2 落地后实测,一个进程常驻的编码参考库 **554 MB**(HPO 48 · Orphanet+IC 77 · HGNC 31 · 基因→HPO 35 · **ClinVar P/LP 351**),
> server worker + 评测薄壳各一份就翻倍。§3.1 选"自有 bundle"是为了绕开 FHIR bundle 重建,没有说过参考库必须常驻内存。

### 16.1 现状:什么已有索引,什么没有

| 参考库 | 现在的形态 | 查法 | 索引 |
| --- | --- | --- | --- |
| HPO 标签/同义词(63,843 键) | `HpoAdapter._exact: dict` | 精确 → 最长包含 | 精确:哈希 O(1);包含:按键长降序的**顺序扫描** |
| Orphanet 名称/同义词 | `DiseaseAdapter._names: dict` | 同上 | 同上 |
| Orphanet HPO 注释闭包 + IC(4,355 病种) | `dict[orpha, frozenset]` + `dict[hpo, float]` | 每次编码对全部病种算 best-match IC | 无(本质是全表计算) |
| HGNC / 基因→HPO | dict | 符号精确查 / 按基因取集合 | 哈希 |
| ClinVar P/LP(348,988 行) | `dict["chrom:pos:ref:alt"]`(pickle 105 MB → 内存 351 MB) | 五元组精确查 | 哈希 |

结论:**点查都有索引,包含匹配没有;问题不在索引而在常驻体积**,且 63% 来自 ClinVar 这一张纯 KV 表。

### 16.2 决策:混合式,大而点查的进库,小而全表算的留内存

| 参考库 | 去向 | 理由 |
| --- | --- | --- |
| ClinVar P/LP | **Postgres** `ref_clinvar` | 纯五元组点查,B-tree 完全胜任;省 351 MB |
| HGNC、基因→HPO | **Postgres** `ref_hgnc`、`ref_gene_hpo` | 同上;省 66 MB |
| Orphanet 名称/同义词/基因/OMIM/ICD | **Postgres** `ref_orpha_*`,`pg_trgm` 做包含匹配 | 查法可用索引表达 |
| Orphanet HPO 闭包 + IC | **留内存**(≈60 MB) | 全表算,逐病种查库是几千次往返;阶段二可试 `ref_orpha_hpo_closure` 一条 `JOIN…GROUP BY…LIMIT k` 出榜 |
| HPO 标签索引 | **留内存**(48 MB) | 每条断言都查,延迟敏感 |

做完后常驻 **≈110 MB**(-80%);闭包也进库则 ≈50 MB。

### 16.3 DDL:`36_rare_reference.sql`(主包只追加;数据不进 git、不进 wheel)

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- 每张参考表都带 source_version:ClinVar 月更、HPO/Orphanet 季更,th_variant_annotation 已按此口径记版本
CREATE TABLE IF NOT EXISTS ref_clinvar (
    chrom          VARCHAR(8)  NOT NULL,          -- 不带 chr 前缀,GRCh38
    pos            INTEGER     NOT NULL,
    ref            TEXT        NOT NULL,
    alt            TEXT        NOT NULL,
    variation_id   VARCHAR(16) NOT NULL,
    clnsig         VARCHAR(64) NOT NULL,          -- Pathogenic / Likely_pathogenic / Pathogenic/Likely_pathogenic
    review_status  VARCHAR(80),
    stars          SMALLINT    NOT NULL DEFAULT 0,
    gene_symbol    VARCHAR(64),
    consequence    VARCHAR(64),
    condition_names TEXT[],
    disease_db     TEXT,                           -- 原 CLNDISDB,含 Orphanet:/OMIM: 链接
    source_version VARCHAR(32) NOT NULL,
    PRIMARY KEY (chrom, pos, ref, alt)             -- 五元组点查走这一个索引
);
CREATE INDEX IF NOT EXISTS idx_ref_clinvar_gene ON ref_clinvar (gene_symbol);

CREATE TABLE IF NOT EXISTS ref_hgnc (
    symbol         VARCHAR(64) PRIMARY KEY,
    hgnc_id        VARCHAR(16) NOT NULL,
    name           TEXT,
    location       VARCHAR(64),
    source_version VARCHAR(32) NOT NULL
);
CREATE TABLE IF NOT EXISTS ref_hgnc_alias (                 -- 别名 / 曾用名 → 现行符号
    alias          VARCHAR(64) NOT NULL,
    symbol         VARCHAR(64) NOT NULL REFERENCES ref_hgnc(symbol),
    kind           VARCHAR(8)  NOT NULL,          -- alias | prev
    PRIMARY KEY (alias, symbol)
);
CREATE TABLE IF NOT EXISTS ref_gene_hpo (                   -- genes_to_phenotype.txt
    gene_symbol    VARCHAR(64) NOT NULL,
    hpo_id         VARCHAR(16) NOT NULL,
    disease_id     VARCHAR(32),                    -- OMIM:nnn / ORPHA:nnn
    source_version VARCHAR(32) NOT NULL,
    PRIMARY KEY (gene_symbol, hpo_id, disease_id)
);
CREATE INDEX IF NOT EXISTS idx_ref_gene_hpo_disease ON ref_gene_hpo (disease_id);

CREATE TABLE IF NOT EXISTS ref_orpha_disorder (
    orpha_code     VARCHAR(16) PRIMARY KEY,
    name           TEXT NOT NULL,
    disorder_type  VARCHAR(64),
    icd10          TEXT[],
    omim           TEXT[],
    source_version VARCHAR(32) NOT NULL
);
CREATE TABLE IF NOT EXISTS ref_orpha_name (                 -- 名称 + 同义词的折叠键,一行一键
    name_key       TEXT NOT NULL,                  -- lexical.normalize(name)
    orpha_code     VARCHAR(16) NOT NULL REFERENCES ref_orpha_disorder(orpha_code),
    kind           VARCHAR(8)  NOT NULL,           -- label | synonym
    PRIMARY KEY (name_key, orpha_code)
);
CREATE INDEX IF NOT EXISTS idx_ref_orpha_name_trgm ON ref_orpha_name USING gin (name_key gin_trgm_ops);  -- 包含匹配
CREATE TABLE IF NOT EXISTS ref_orpha_gene (
    orpha_code     VARCHAR(16) NOT NULL REFERENCES ref_orpha_disorder(orpha_code),
    gene_symbol    VARCHAR(64) NOT NULL,
    hgnc_id        VARCHAR(16),
    association    VARCHAR(80),                    -- Disease-causing germline mutation(s) in / Major susceptibility factor in / ...
    PRIMARY KEY (orpha_code, gene_symbol)
);
CREATE TABLE IF NOT EXISTS ref_orpha_hpo (                  -- phenotype.hpoa ORPHA 行(闭包仍在内存算)
    orpha_code     VARCHAR(16) NOT NULL REFERENCES ref_orpha_disorder(orpha_code),
    hpo_id         VARCHAR(16) NOT NULL,
    frequency      REAL,                           -- HP:0040280..85 折成点估计;NULL = 未标
    PRIMARY KEY (orpha_code, hpo_id)
);
CREATE INDEX IF NOT EXISTS idx_ref_orpha_hpo_term ON ref_orpha_hpo (hpo_id);
```

索引取舍:ClinVar 只留主键 + 基因索引(月更 35 万行,索引越多装载越慢);Orphanet 名称表用 `pg_trgm` GIN 是为了"文本包含病名"的查法,精确查仍走主键;`ref_orpha_hpo` 的 `hpo_id` 索引给 `rank_rare_diseases` 阶段二进库用。

### 16.4 装载与版本

- 插件命令 `mirobody-rare-load-reference [clinvar|hgnc|orpha|all]`:源文件由 `res/EXTERNAL.tsv` 登记(不进 git),按 CLAUDE.md **分批、可重跑只补缺失**——先 `SELECT DISTINCT source_version` 判断该版本是否已装,同版本跳过,新版本 `ON CONFLICT DO UPDATE` 并把旧版本行标 `retired`(阶段二)或直接覆盖(MVP)。

**VCF 摄取的硬规则**:一条染色体十几万个 call,**禁止逐行查库**;按染色体分片后把过滤后的五元组一次性送进 `JOIN ref_clinvar`,与现有 ≤8 并发分片结构配合。

### 16.6 代价与验收

- 点查从 dict 微秒级变毫秒级;每例编码多几十次查库,评测薄壳 60 例实测对比前后耗时,**慢于 2× 就回退到 memory 后端**。
- 验收:① 32–36 号 DDL 对干净库连跑三次零错误;② `reference.backend=pg` 与 `memory` 对 haenv `rare_coding-p1` 60 例的 `rc_*` **逐位相同**(后端只换存储,不换答案);③ 装载器中途 kill 后重跑,行数不变、无重复;④ 进程常驻 ≤ 150 MB。
- 前提:本机尚无 Postgres,`PgRepo` 至今只写未回放;先起库(`compose.yaml`)回放 32–35 号 DDL 与 `PgRepo`,再做 ClinVar 进库。

推进顺序:ClinVar → HGNC/基因注释 → Orphanet 名称表;HPO 索引与相似度闭包留内存,真实病例量上来后再评估。

### 16.7 补充(2026-09-21 实测后)

**索引现状与提速空间**(本机实测,中位数):

| 查法 | 现状 | 加索引后(原型) | 倍数 |
| --- | --- | --- | --- |
| HPO / Orphanet / HGNC / ClinVar 精确点查 | 0.005 ms 以下(哈希) | 不变 | 已最优 |
| HPO 包含匹配(顺序扫 64k 键) | 8.2 ms | 0.01 ms(最稀有二元组倒排) | ≈800× |
| Orphanet 病名包含匹配(扫 26k 键) | 2.7–3.8 ms | ≈0.01 ms(同法) | ≈300× |
| 病种表型排序(4,355 病种全算) | 230 ms | 83 ms(term→病种倒排预筛到 ≈1,200 候选,top-5 不变) | 2.8× |

折到一例:词表部分 ≈0.35 s → ≈0.1 s;整例中位 2.1 s(带 VCF 5–9 s)的大头是解压顺序读 VCF 与算 DICOM sha256,词表索引只省约 15%。
下一步该优化的是 VCF 读取(bgzip + tabix 按区间取)。倒排原型的平票顺序尚未做成确定性,正式实现须保持「最长优先、同长按注释频次」,验收仍是 `rc_*` 逐位不变。

**Postgres 不是为速度**:`ref_clinvar` 点查约 0.2–1 ms,比内存哈希慢;换来的是常驻内存 -351 MB、多进程共享一份、词表版本可审计。

**`ref_clinvar` 主键改为 md5**:btree 单行上限约 2.7 kB,ClinVar 含更长的缺失/插入等位基因,五元组直接作主键在装载时报 `index row size exceeds btree maximum`。
改为生成列 `vkey = md5(chrom:pos:ref:alt)` 作主键,`(chrom,pos)` 另建索引供区间扫描;`lookup_many` 对 `unnest` 的查询元组算同一 md5 再 JOIN。§16.3 的 DDL 以 `36_rare_reference.sql` 落盘版本为准。

**部署**:测试库 `mirobody_test`,schema **`mirobody_rare`**(不用 `public`,与主包 `mirobody_ai` 隔离);连接串由 `MIROBODY_RARE_PG_DSN` 给,插件连接池对每条连接 `SET search_path`,
32–36 号 DDL 用 `mirobody_rare.reference.run_schema()` 回放(三次零错误已验)。装载命令 `mirobody-rare-load-reference [clinvar|hgnc|gene_hpo|orpha|all]`。

### 16.8 落地实测(2026-09-21,测试库 `mirobody_test` · schema `mirobody_rare`,AWS 远端)

**装载**:`ref_clinvar` 348,988 行 271 s(4.47M 条 VCF 扫描 + 暂存表 COPY + 一次合并)· `ref_hgnc` 45,083 + 别名 60,713 · `ref_gene_hpo` 333,888 · Orphanet 病种 11,645 / 名称键 26,952 / 基因关联 8,503 / HPO 注释 115,745。
同版本重跑全部 `skipped`(版本键 = 源文件 mtime 日期)。32–36 号 DDL 三次回放零错误。

**两个被实测推翻的假设**:

1. **"点查进库"在远端库上不成立**。到测试库的往返 ≈500 ms;一例 VCF 有 13–50 万个五元组,即便 `unnest` 一次送 15 万条也要 8 s,trio 例 30–70 s(内存后端 5 s)。
   改为**键在本地、载荷在库**:进程启动时取 349k 个 `vkey` md5 摘要(16 B/个,≈35 MB,按 `source_version` 落盘缓存,首取 28 s),`lookup_many` 本地算 md5 过滤,只为命中的几条发一次 `WHERE vkey = ANY($1)`。
   trio 例 50 万元组 → 1.1 s、一次往返。这仍是 §16.2 的目的(常驻内存从 351 MB 降到 67 MB、载荷与版本在库里可审计),只是"点查"发生在本地键集上。
2. **asyncpg 连接池会 `RESET ALL`**,`init` 里的 `SET search_path` 在连接归还后失效,DDL 与装载静默落进 `public`。改为 `server_settings={"search_path": ...}`(启动参数,不被 reset);误建的空表已清理。
   另:`ref_clinvar` 五元组直接作主键在装载时超过 btree 单行 2.7 kB 上限(长缺失/插入),改为 md5 生成列主键 + `(chrom,pos)` 索引。

**等价性与代价**(60 例经两个薄壳各跑一遍,比较 `assertions/abstained/diagnosis/gene/variants/differential/signals`):
**60/60 逐位相同**;延迟中位 4.72 s → 6.64 s(**1.41×**,≤2× 线内);薄壳常驻 608 MB → **352 MB**。
常驻**未达 ≤150 MB**:ClinVar 这一项 351 → 67 MB 已兑现,剩下 HPO 48 + Orphanet 闭包 77 + HGNC 31 + 基因→HPO 35 仍在内存 —— 后两者已装进库,切客户端即可再降 ≈60 MB;HPO 与闭包按 §16.2 留内存,150 MB 这条线要靠它们瘦身(HPO 索引只留 zh/en 标签键、闭包改 int 编码)才够得着。

**还留在内存里的**:HPO 索引 48 MB、Orphanet 闭包 + IC 77 MB、HGNC 31 MB、基因→HPO 35 MB。HGNC 与基因→HPO 已装进库但客户端未切换(阶段二,同"键本地/载荷在库"模式或直接点查,它们每例只查几十次)。

## 17. 大文件:哪些会大、现在会怎么坏、怎么改(2026-09-21 补充)

> 触发:部署后经前端同一条 websocket 路由实测上传,链路能通,但整条路是**按小文件设计的**。
> 下面的量级来自盘上真实文件(`glodata/rare/`),不是估计。

### 17.1 哪些文件会大

| 类别 | 典型大小 | 盘上实测 | 备注 |
| --- | --- | --- | --- |
| VCF · panel | 1–20 MB | — | 现有路径没问题 |
| VCF · WES | 50–500 MB(bgzip) | GIAB 高置信集 chr1–22 **126 MB** | 单样本 3–5 万 call;§0.2 的 MVP 上限 |
| VCF · WGS | 5–100 GB | — | 400–500 万 call;明确阶段二 |
| **gVCF / 多样本 VCF** | 1–10 GB | — | 家系联合 call 常是一个多样本文件,不是三个单样本 |
| DICOM 系列 zip | 50 MB–2 GB | UPENN-GBM 单患者 **1.8 GB**,单系列最大 **452 MB** | MRI 多序列、CT 薄层;病理 WSI 单张 1–5 GB |
| EEG(EDF) | 100 MB–5 GB | — | 长程视频脑电 24 h 可达数 GB;阶段二 |
| FASTQ / BAM / CRAM | 5–200 GB | — | 不在任何阶段范围内,但用户会传:必须**明确拒收并说明**,不能静默失败 |
| 参考库 | ClinVar VCF **185 MB**、Orphanet XML 54 MB | — | 不走上传;§16 已进库 |

### 17.2 现在的路径在哪里会坏(实测代码路径)

1. **websocket 上传把整个文件攒在内存里**:`file_upload_manager` 每片 base64 解码后 `bytearray.extend`,直到收齐;两个 400 MB 的 DICOM 系列同时传就是近 1 GB 常驻,再加 base64 膨胀 33%。
2. **处理阶段再整读一遍**:`handlers/base.py` 的 `_extract_original_text` / `_extract_abstract`、`file_uploader.upload_file_and_get_url` 都是 `await file.read()`;插件的 `is_dicom_zip` 也把整个 zip 读进内存只为看中央目录。
3. **只有一道尺寸门**:`ingest.MAX_VCF_BYTES = 500 MB`,在文件已经完整落到临时目录之后才判;DICOM、PED、FASTQ 没有任何门。
4. **处理在 server 进程内 `spawn`**:一个 WES 解析 20–60 s 占着事件循环所在进程的 CPU;两个并发就影响所有请求。
5. **一次处理即一次全量扫描**:VCF 用 gzip 顺序读,没有 tabix;DICOM 对每个 zip 完整算 sha256(452 MB 约 2 s,可接受,但 WSI 5 GB 就是 20 s)。
6. **上传管理器每收齐一个文件就启动一次处理**(§impl 记录的双处理问题),文件越大重复代价越大;插件侧已按内容哈希去重,但重复的字节已经上传并落盘了。

### 17.3 改造(按收益/代价排序)

| 序 | 改什么 | 落点 | 效果 |
| --- | --- | --- | --- |
| 1 | **入口就判尺寸与类型**:`upload_start` 的 `files[].size` 与扩展名先过门 —— 超过阈值或属 FASTQ/BAM/CRAM 直接 `upload_error` 并说明("MVP 支持 panel/WES,WGS 与测序原始数据请联系…"),不接收任何 chunk | 主包 `file_upload_manager.handle_upload_start`;阈值进 config(`UPLOAD_MAX_BYTES_BY_KIND`) | 拒收发生在传输之前,不在落盘之后 |
| 2 | **分片直落磁盘 / 对象存储,不攒内存**:每片写 `SpooledTemporaryFile`(超 16 MB 转磁盘)或直接用对象存储的分片上传(S3 multipart);处理阶段只拿路径 | 主包 `file_upload_manager`、`temp_manager` | 常驻内存与文件大小解耦 |
| 3 | **二进制类型不走文本路径**:factory 命中插件处理器后,`base.process` 不再调 `_extract_original_text` / `_extract_abstract`(现在靠处理器返回空文本绕开,但 `file.read()` 仍会发生一次) | 主包 `handlers/base.py` 加 `binary = True` 类属性短路 | 省一次整读 |
| 4 | **插件探测只读头部**:`is_dicom_zip` 改读 zip 中央目录(`zipfile` 只需 seek 到文件尾);`is_vcf` 已经只读 256 B | 插件 `handlers.py` | 探测成本与文件大小无关 |
| 5 | **VCF 要求 bgzip + tabix,按区间取**:有 `.tbi` 时用 pysam 按染色体取,没有则整扫但并发 ≤8;多样本 VCF 按样本列拆成多个 `th_sequencing_sample`,PED 对齐样本列名 | 插件 `variant/vcf.py`、`ingest.py` | WES 分片解析从 20–60 s 降到秒级;家系联合 call 可用 |
| 6 | **处理挪出 server 进程**:`spawn` → `mirobody worker` 队列,任务键 (user, content_sha256),同键去重(顺手解决 17.2-6) | 插件 `handlers.py` + 主包 worker | server 不被解析占死;重复上传只处理一次。**阻塞**:worker 队列以 Redis 为任务源与执行锁(`task/base.py`),部署环境无 Redis;先以内容哈希去重(已做)顶住重复处理 |
| 7 | **原始 call 不进库**:WGS/WES 全量 call 转 Parquet 进对象存储,库里只留候选与版本化注释(§16 与 1 TB 讨论的结论) | 插件 `ingest.py` | 库体量与文件体量解耦,月更重注释可增量 |
| 8 | **大对象直传**:前端对 >100 MB 的文件走对象存储预签名分片上传,server 只收 `file_key`;DICOM/WSI/EDF 都走这条 | 前端 + 主包 `/files/upload` 预签名接口 | websocket 只承担进度,不承担字节 |
